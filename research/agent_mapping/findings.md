# TvC executable research

## Continuation: stage-specific bounds with giant-class characters

**Observed, high confidence for the conditions and constants:** `0x80039b04` (file `0x23fe4`) is called by the larger update routine `0x80039c14`. It calls `0x80057c3c`, which walks slots 0..3 and returns true if a resolved fighter both has `+0x44a0 == 1` and passes `0x80057c04`'s ID test: 11, 22, 23, 24, or 25. Existing Continuo mappings identify those as Gold Lightan, PTX-40A, and the three Yami IDs; `+0x44a0` is documented as the point flag, but the full behavior of every mode needs testing. When that test is true and stage-result global `0x803eb8f4 == 4`, the routine clamps an object float at `+0x08` to at least float32 `0.64` and `+0x44` to at least `2.33`; for other stage results the minima are approximately `0.24` and `1.33`. It additionally clamps object `+0x40` to approximately `[-6.2, 6.2]` when the test is true and `[-8.1, 8.1]` otherwise. The constants come from the DOL's initialized r2-relative data. Continuo's stage-select code associates stage value 4 with Wasteland, but the object and its fields have not yet been proven to be camera or stage-boundary fields.

### Continuo application

This is a useful explanation candidate for stage- and giant-dependent camera or positioning behavior and could help test overlay drift or stage overrides. Read `0x803eb8f4`, fighter IDs and `+0x44a0`, and the object's `+0x08`, `+0x40`, and `+0x44` once its pointer is established; identifying the object at the call can require a debugger or hook. Changing bounds would require writes or a patch. Runtime test: record the object and fields at `0x80039b04` for stage result 4 and another stage with normal and giant-class point characters; compare camera movement and player positions before naming the fields.

## KO control: per-fighter KO flag and input-history clearing

**Observed, high confidence for static paths:** The routine containing `0x80052420` begins at `0x80051e20` (file `0x3c300`); it is a broader HP/state updater, not an independently recognized function beginning at `0x80052420`. In one branch, if fighter current HP `+0x28` is below 1, the mode and state gates allow it, and fighter `+0x7c` bit 0 is clear, the code sets fighter main word bit `0x1000` and records whether that bit was previously clear. Other branches can restore HP, use training-related logic, or skip this transition. During native state 4, the first-time KO path resolves the paired fighter with `0x80058024`; when that pointer is null or its main word also has bit `0x1000`, and another per-slot condition is satisfied, it sets `0x8047a920` bits 0 and 1 and invokes `0x80053540` with specific arguments. The label or meaning of that downstream event has not been independently verified. A single fighter's `0x1000` bit alone therefore cannot establish a full-team KO or live result screen.

`0x80076300` (file `0x607e0`) is called immediately after `0x800767b0` from the same fighter-update function `0x8005485c`. It clears fighter `+0x13c8..+0x13e0` if the KO bit is set outside the specified mode/state exceptions, or if director `+0x0c < 1`; otherwise it iterates 32 input bits and updates per-bit counters around `+0x1278` and `+0x12f8`, and masks at `+0x13d8/+0x13dc` using thresholds 7, 12 and 16. Exact input-buffer semantics and whether those counts match rendered frames are not yet established. This corroborates why the existing KO Control code treats raw-pad routing and later clearing as separate gates. These observations are about the unmodified executable, not a new patch recommendation.

**Downstream event dispatcher:** `0x80053540` writes its arguments to runtime globals `0x804784b0`, `0x804781a4` and `0x804781a8`, then calls `0x80156b14` with event group `0x10`. The latter indexes a table through the pointer at `0x80561460`, using a `0x30`-byte group stride; `0x80156a58` walks the selected list and calls each nonzero callback at node `+0x08`, subject to its arguments and a counter. This describes generic dispatch, not an independently identified win-screen or quote callback. The same dispatcher has other callers. A live callback list may reveal the current result route, but node lifetime and safe traversal bounds are not established.

### Continuo application

KO Control could diagnose *which* native condition is suppressing movement by displaying the fighter KO bit, partner pointer/bit, director `+0x0c`, mode `0x803eb7dc`, and `+0x13c8..+0x13e0` before and after the two input functions. Reads can show stable state; distinguishing within-frame writes requires a hook or debugger. Changing the behavior requires the existing project's writes/patches and is outside this research pass. Runtime test: record a first-character KO with a living partner, a full-team KO, winning and losing point fighters, results, rematch and tag transitions; correlate function entry and input fields with actual movement and the existing SAFE/FULL/OFF states. Include training and null/giant-partner cases before generalizing.

## Karas and Soki character-specific combat checks

**Observed, high confidence for branch conditions:** Collision-path helper `0x801415bc` (file `0x12ba9c`), called at runtime `0x8004ed58` from `0x8004dfd4`, has an explicit Karas branch for character ID 10 and action IDs `0x13e..0x140`. Within a broader branch requiring input word `param_4` bits `0x4` and `0x80000`, the Karas case also requires bit `0x2` and another fighter's `+0x58 & 0x200` or `+0x60 & 0x40`; it then sets a local return flag and clears that other fighter's `+0x64` bit `0x20000000`. Nearby Yatterman-1 ID 5 actions `0x133..0x135` receive a similar but not identical check requiring `param_4 & 2 == 0`. The helper contains other independent branches that can set the same return flag; its full combat meaning is not proven. This is a strong Karas-specific lead, but it does not establish a counter mechanic or equivalence to Joe's Cactus Bunker branch.

Separately, `0x801455a0` (file `0x12fa80`) has a Soki ID 21 branch for actions `0x136..0x138` and fighter float `+0x1d8 >= 15.0`; it sets a local eligibility boolean within a much larger action/state selection routine. The same successful path later writes Baroque-related `+0x44bc`, `+0x454c` and recoverable health, so this is a useful Baroque/action-interaction lead, not proof that these action IDs are counters. The project move CSV has character-specific counter labels, but also contains inconsistent hexadecimal mappings; do not equate those labels with these static IDs without a live trace.

### Continuo application

These checks could improve character-specific explanations when protection or action eligibility differs from generic rules. Read fighter ID, `+0x1e8`, `+0x58`, `+0x60`, `+0x64`, Soki `+0x1d8`, and the relevant contact property word; capturing the helper's actual arguments and return at the contact edge may require an existing recorder hook or debugger. Changing these branches requires writes or a patch. Runtime test: record Karas actions `0x13e..0x140` and Soki actions `0x136..0x138` against controlled contact and Baroque scenarios, then compare with Joe's known Cactus Bunker `0x139..0x13b`. Verify action names from the live game before assigning the counter label.

## Native music, voice and sound-bank initialization

**Observed, high confidence for paths and control flow:** `0x80191d38` (file `0x17c218`) initializes separate resources named `snd/stream/us/bgm.srt` and `snd/stream/us/vo.srt` into two separately allocated `0x5000` buffers, then calls `0x8011bb74` with path-pointer table `0x8038af50`, count `0x41` for group 0, and `0x8038b058`, count `0x3c` for group 1. The latter helper reads four 32-bit offsets from the buffer, adds the buffer base to each, and registers those addresses along with the table pointer and count. The decompilation does not prove the exact file format or success behavior. Small-data startup state at runtime `0x80561698` gates repeated initialization; buffer pointers are stored at `0x8056167c` and `0x80561680` in this build.

The 65-entry first table contains `dummy.ssd`, repeated `temp.ssd`, `s_bgm_19.ssd` through `s_bgm_47.ssd`, then `stage_01.ssd` through `stage_14.ssd` at table indices 48..61, `stage_17.ssd` at index 62, and null entries at 63 and 64. The 60-entry second table contains 20 entries each pointing to `dummy1.ssd`, `dummy2.ssd`, and `dummy3.ssd`. Exact paths and all indices are in `native_audio_stream_paths.csv`, reproducible with `export_audio_tables.py`; representative pointer words were checked against the open Ghidra image. These table indices are stream-table indices, **not** proven stage IDs or proof that the second table describes all character voice lines.

**Registration structures:** `0x8011bdac` returns fixed runtime base `0x8042b158`; `0x8011bdb8` selects `base + 0x48 + group*0x28`; `0x8011be20` stores the supplied table pointer and count at selected record `+0x20` and `+0x24`. Therefore this initialization writes the BGM table pointer/count to `0x8042b1c0/0x8042b1c4` and the second group's pointer/count to `0x8042b1e8/0x8042b1ec`. These are observed registration fields, not active stream indices or AX voices. The program loop at `0x800de008` calls sound initialization when its own state `0x80478194` is 3 and `0x80478198` is 9; scene names are not statically established.

`0x80191040` separately formats each supplied base path with `.tsb` and `.whd`, requires both file-size queries to be nonzero, allocates separate buffers and invokes the file loader for both. Initialization supplies the bases `snd/se/us/se_sy0`, `snd/se/us/se_sys`, and `snd/se/us/se_com`. Thus the executable has sound-bank loading paths beyond the two stream lists. The Doronjo/Saki pair-selector's returned value has not yet been connected to either a bank or a voice playback call; voice lines remain a plausible hypothesis, not a finding.

**Additional scene-specific banks:** `0x80191b40` selects `snd/se/us/se_mgcm` when its second argument is -1, `se_mg00` for 0 or 10, and `se_mg22` for 20 or 22, then invokes the paired-bank loader. `0x80191c4c` similarly selects `se_mg22_gac`, `se_mg22_ryu`, or `se_mg22_tkb` for arguments 1, 2, or 3. These resource names suggest mini-game and character associations, but the argument semantics and playback use require validation. In `0x801341d8`, mode 21 loads paired-bank slot 8 from `snd/se/us/se_csl`; its scene name is unproven. `0x801911d0` unregisters and frees both buffers for a supplied bank slot and clears their pointer slots when the first buffer is nonzero. Buffer arrays include `0x8048c2c0` and `0x8048c298` indexed by `slot*4`; they are distinct from the stream registration records.

**Character-ID bank dispatch, including Doronjo:** `0x80191260` (file `0x17b740`) dispatches its second argument, limited to 0..32, through a jump table at runtime `0x8038b148`. The case code formats a base under `snd/se/us/` and calls the paired `.tsb`/`.whd` loader `0x80191040`. For ID 20, the selected base is `se_pl20` (Saki in Continuo's fighter-ID map); ID 27 selects `se_pl34` (Joe), ID 29 selects `se_pl36` (Zero), and IDs 23–25 all select `se_pl23` (Yami forms). These associations assume this caller's selector uses the same IDs, which matches the table but still warrants a live trace.

The ID-6 case is exceptional: a fourth argument controls six branches. Values 0, 1, 2, 3, 4, 5 select `se_pl06`, `se_pl28`, `se_pl29`, `se_pl30`, `se_pl31`, `se_pl32`; other values fall back to `se_pl06`. Continuo identifies ID 6 as Doronjo. The raw jump-table entries and instructions agree with the instruction comments in the archived DolRecomp output, but this Ghidra flat image does not recognize the indirect case blocks as functions; DolRecomp chunk boundaries were not treated as function boundaries. This directly supports multiple Doronjo sound-bank variants. **It does not yet link the fourth argument to the earlier Doronjo/Saki value or establish that these variants are matchup voice lines.** A separate ID-11 case chooses between `se_pl11` and `se_pl27` using the third argument; its gameplay meaning is also open.

**Matchup-specific bank selection, strong support for the voice hypothesis:** A caller in the sequence interpreter at executable `0x80118f50..0x80119094` checks the selected object's `+0x14 == 6`, then for its side field `+4` equal to 0 or 1 looks up the other primary slot through `0x80057d18`. For other-slot character ID 13 (Chun-Li), it passes variant 2 to `0x80191260`, selecting `se_pl29`; for ID 5 (Yatterman-1) or 28 (Yatterman-2), variant 3 selects `se_pl30`; for ID 20 (Saki), variant 4 selects `se_pl31`. For other IDs it calls `0x8014c9cc(0,2)` and uses its return as the variant; its distribution is unverified. If the other fighter lookup fails, the selected variant comes from the earlier branch state. At `0x80119094`, the caller passes bank slot `selected_object[+4] + 3`, character ID `+0x14`, another field `+0x18`, and the matchup-selected variant. A second interpreter call at `0x80119f40` explicitly passes variant 5, selecting `se_pl32` when its character argument is 6; its scenario is not yet known. Key instruction words at `0x80118f78`, `0x80118fc8`, `0x80118fec`, `0x8011903c`, `0x80119060`, and `0x80119094` match between the archive and open Ghidra image. The 0/1 slot relationship matches Continuo's primary slots, but confirm behavior in other game modes. **Conclusion:** matchup-dependent Doronjo sound-bank selection is statically established. Specific voice clips and the relationship to the separate `0x80070e64` return remain unverified.

**Stage sound-bank dispatch:** `0x801918a8` dispatches a second argument from 0..15 through a table at `0x8038b1cc` and formats `snd/se/us/se_map00` through `se_map15`. Cases 0, 5 and 11 format a name but branch to the routine's exit without calling the paired-bank loader; the other 13 cases call `0x80191040`. An interpreter call at `0x8011912c..0x8011913c` passes bank slot 7 and loads the second argument directly from stage-result global `0x803eb8f4`. Thus in this call path stage result 15 selects `se_map15`, while results 0, 5 and 11 skip this particular bank load. The relevant branch and call instruction words match between the archived DOL and open Ghidra image. The unrecognized jump targets were traced as instructions, not treated as independent function boundaries. These special cases do not prove the stages lack sound, because common banks or other paths may supply it. Verify the live cursor-to-result transition and available bank assets before assigning displayed stage names.

**Character sound request path:** `0x80190ebc` combines its first integer argument with `(second argument + 3) * 0x10000`, then calls `0x80190ea0`, which splits that value into high and low 16-bit parts and passes them to `0x8011e2c0`; the latter calls a lower-level sound-manager function. For a nonnegative first argument below `0x10000`, this gives bank-like group `second argument + 3` and the original low-16-bit ID. A sequence-interpreter call at `0x801195bc` passes a resolved operand as the first argument and another resolved operand as the second. This is a concrete path for script-driven character sound requests, but no static sequence bytes have yet been shown that feed the earlier Doronjo pair selector's `0x168` into this call; do not claim that linkage or that every request is a voice line. The packed arithmetic can carry for other input ranges, so the simple split is conditional.

### Continuo application

The two stream groups and path tables offer concrete targets for diagnosing native music initialization, stage-stream selection and music replacement across select/loading transitions. Continuo can read the initialization flag, buffer pointers, registration fields `0x8042b1c0..0x8042b1c4` and `0x8042b1e8..0x8042b1ec`, along with its existing `0x803eb8f4` stage result; identifying the active table index or file request reliably may require a hook or debugger at `0x8011bb74`, `0x80191040`, or the eventual stream-start routine. Suppressing or replacing game audio requires writes, a hook or a patch; none was performed here. Runtime test: log both group registrations and subsequent stream requests during character select, stage select, match start and result screens; compare index/path to the existing AX voice-pair detector and listen for uninterrupted native voice/SFX. Specifically trace `0x80119094` and `0x80191260` for Doronjo versus Saki, Chun-Li, both Yattermen, and a control; verify the selected bank and listen for matchup-specific lines. Trace the earlier Doronjo pair selector independently before linking its return value to these banks.

## Character-select resource tags and generated texture names

**Observed, high confidence for this DOL:** The initialized pointer table at `0x803690d0` has 33 contiguous short resource tags followed by a null word, exported in `native_character_resource_tags.csv` by `export_character_tags.py`. Examples include ID 6 `dro`, 10 `krs`, 20 `sak`, 21 `yuk`, 23–25 `tk1`/`tk2`/`tk3`, 27 `joe`, and 29 `zer`; index 0 is `cmn`, index 9 is `ts2`, and indices 31 and 32 are `tst` and `lst`, even though Continuo's current fighter map does not use ID 9. A tag existing in this table alone does not establish a playable character or asset availability. Representative table pointers match the open Ghidra image.

The character-select sequence-handler region at `0x800e8268..0x800e8390` resolves operands and indexes that tag table; its formatting branches use DOL format strings `%s.tpl`, `%s%s.tpl`, or `%s%s_r.tpl`, then pass the generated name to `0x800a745c`. The initial prefix is supplied by the sequence/context, not fixed by these format strings. The relevant instructions span two DolRecomp chunks; they are one continuous runtime address range, not evidence of two original functions. Ghidra has no recognized function or instruction at the handler's queried flat offset, so this observation comes from the archived DOL/generated instruction comments and should be cross-checked against live execution. It supports Continuo's existing select-resource research and explains why a resource tag such as Soki's `yuk` need not match the character's English name.

**Two-character name construction and a Gold Lightan special case:** In another sequence-handler region at `0x80117b7c..0x80117db0`, two separate resolved values are loaded at `0x80117bd8` and `0x80117bf8` and used to construct two names using the same native tag table. For the first value, when the character ID is 11 and another resolved mode is 1 or 3, the code substitutes format `%ssil` instead of its normal tag-appending format. Continuo maps ID 11 to Gold Lightan; the `sil` string suggests a silhouette variant but that visual meaning is inferred. The second name is constructed separately. Five key instruction words including both value loads and the ID-11 comparison match the open Ghidra image. Continuo's select code associates this handler with an inner sequence opcode; its exact use on versus or win screens needs runtime confirmation rather than assuming all screens share the same path.

### Continuo application

An inspector could show the actual native tag and constructed texture name when diagnosing missing portraits, names, or extended-character assets, rather than guessing tags from display names. The static table is readable; observing the sequence prefix, operands and exact requested name may require a hook or debugger at the handler or `0x800a745c`. Replacing a selection resource requires writes or a patch. Runtime test: capture generated names for stock characters, Saki, Soki, and each Yami form in select and versus screens; compare loaded assets and the game's display, and explicitly test index 9 without assuming it represents a usable roster entry.

**Observed, high confidence:** `0x8014121c` (file `0x12b6fc`), called from contact processing at `0x8004e2bc` (file `0x3879c`), compares attack property bits `0x08`, `0x10`, `0x20` against defender `+0x244` masks `0x02000000`, `0x04000000`, `0x08000000`. ## Doronjo / Saki pair-specific selector

**Observed, high confidence for the comparisons; low confidence for purpose:** `0x80070e64` (file `0x5b344`) calls `0x80057e34` twice, once with its incoming integer and once with 1 if that integer is zero, otherwise 0. The lookup scans up to four objects resolved through `0x80057d18`, returning an object whose `+8` equals the requested value, subject to a global byte gate. If either lookup fails, the selector returns zero. Otherwise it starts with a 32-bit table entry at runtime `0x8034ed10 + first_object[+0x14]*4`. When the first object's ID is 6 (Doronjo), it substitutes `0x168` for second-object ID 20 (Saki), `0xf0` for ID 5 (Yatterman-1), or `0x14a` for ID 13 (Chun-Li). Instructions at file `0x5b388..0x5b3c8` confirm the ID loads, comparison, and `0x168` return candidate. The result's meaning and whether the objects represent opposing characters, partners, or another slot relationship are unresolved. This is not evidence of Saki's helmet mechanic.

**Sequence-interpreter consumer:** The call at `0x800ff1a4` receives an operand resolved by `0x800e0380`, invokes the pair selector, and writes the result to interpreter object `+0x4c` and `+0x54`. ### Continuo application

## Character-specific six-byte entry selector

**Observed, medium confidence for purpose:** `0x80064b9c` (file `0x4f07c`) selects an entry from a structure with count byte `+0x22` and six-byte entries starting near `+0x32`; it returns an index or -1. That structure points at an owner through `+0x98`. For owner character ID 6 (Doronjo), action `+0x1e8 == 0x150` causes a one-time flag update: on entry index 0, if owner `+0x45fc & 0x20` is clear, it sets structure bit 0 and owner bit `0x20`; other actions clear the owner bit. A parallel branch for ID 7 (Ippatsuman), action `0x170`, uses owner `+0x460c` bit 0. The caller `0x80064d94` also clears structure byte `+0x23` and bit `0x10` for these character/action pairs before evaluating entries; `0x80064d30` copies a selected entry into current state when the selected identifier changes. The structure's role and whether the flags affect audio, effects, animation, or another system are unknown; do not infer a named character mechanic from these generic operations.

### Continuo application

This is a concrete lead for explaining why the same character action can select different internal entries only once.
